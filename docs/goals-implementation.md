# Native session goals

Each ordinary conversation owns one current goal. New conversations start with Goal mode off and no Goal tab in the task strip. Selecting **Goal mode** from the composer's **+** menu shows only its bottom icon and Goal label and updates the editor placeholder, without creating a goal or granting execution. The new-conversation layout, project picker, backdrop and draft stay in place until a message is sent. Sending the composer message creates and activates the goal, then reveals the Goal tab; the panel opens only when clicked. Its current-goal content is the submitted user message. Limits can be adjusted in the panel after creation, and verification defaults to the requested outcome in that message. The existing Todo list remains the task source; there is no second task list. Children and scheduled-run conversations cannot create or run goals.

Composer intent/draft/submitted state belong to the renderer's per-conversation store, separately from native Goal revisions. Selection, pending creation and refused sends keep the Goal tab hidden, including when an ended previous record remains in history. Creation pins the native session, goal ID and revision and returns after recording/admitting work; it does not await the SDK run. The editor releases its text/attachments immediately and remains editable while IPC is pending. A renderer-owned optimistic user row and waiting indicator appear in the same frame before native capture/IPC finishes; newer preflight snapshots retain that row. Refusal removes only the originating uncommitted row, and actual SDK user events reconcile it to one bubble. An SDK-handled input, pause/cancellation before acceptance or recovery snapshot retires that exact provisional row and its wait state while retaining the native Goal/input; other messages and chats remain intact. Pending admission prevents duplicate submission; Stop and Escape still cancel preflight. A refusal restores the old draft without overwriting newer input and reports beside the composer; late receipts update only their originating conversation. Successfully used optional criteria are cleared for the next goal. Invalid unsaved limit edits from an ended goal revert to its saved limits when selecting a new mode.

The panel's bottom **End** button cancels a nonterminal goal through the ordinary Stop path, then hides the Goal panel/tab and composer mode control. Goal records and lifetime accounting remain. Ending an unstarted or cancelled mode only changes renderer intent. Ending a completed mode fsyncs a private dismissal fact while retaining its completed outcome, proofs and ledger. Completed goals remain visible after switching/restarting until explicit End; a late restored metadata event also restores this presentation after an empty startup snapshot. Pause keeps the mode visible and requires explicit Resume. Messages sent while an unfinished goal already exists are ordinary user instructions: they neither replace the objective nor implicitly resume a paused goal. After completion/End, another explicitly selected send can create a new goal. A restored unfinished goal remains discoverable but execution is paused. The panel shows one current-goal/criteria view; editing replaces it. Proof summaries, source identities and file hashes expand per criterion, while allowance fields are collapsed. Completed goals have no second optional acceptance input or duplicate completion summary.

## Ownership and persistence

`src/shared/goal.ts` owns IPC data. `main/pi/goals/runtime.ts` owns state, SDK settlement and continuation admission. `goals/tools.ts` registers `get_goal` and model-only `update_goal`; the latter returns a receipt, and only a committed successful top-level result changes state. Context guidance is request-only and survives compaction/reload through the session's owned loader. `GoalPanel` composes beUI inside the existing `SessionTasks` overlay.

Goal definitions, criteria, limits and explicit transitions are private `pith_goal_v1` entries on the complete selected SDK branch. Successful `update_goal` receipts also fold into branch state, covering a crash between result persistence and its redundant state record. Explicit transitions use the existing session append/fsync boundary. Restoration adds an effective execution pause without appending to the SDK branch: reviewed preview leaves, file-only restores and crash journals must retain their exact endpoints. Reopening an active branch always pauses it; only explicit Resume can grant execution again. Goal metadata has a per-session revision independent of transcript `eventSequence`; null updates are revisioned tombstones, and late action responses stay with their originating conversation.

The independent `<userData>/goals/` ledger starts under its originating session ID and goal ID. Fork aliases resolve directly to that owner pool; spent continuations, reported tokens and billed-entry identities are shared, while each session retains its own dispatch, progress fingerprint and no-progress count. Locked atomic replacement, file fsync and directory fsync protect its usage, billed-entry identities, progress fingerprint and dispatch claim. It is outside conversation branches: Rewind, Resume and ordinary branch restoration cannot refund used allowance. An unavailable, missing or malformed existing ledger stops automatic execution and exposes unavailable accounting. Goal entries alone never grant execution or create a replacement zero-usage ledger. SDK startup suppresses only identical initial model/thinking metadata on pre-message branches, preserving exact reviewed/Rewind leaves; intentional changed selections still append normally.

## Lifecycle

The initial composer send becomes an ordinary user prompt, so Rewind captures its normal before-turn checkpoint. Image attachments follow SDK validation/normalization; files are read using the captured conversation's cwd. Input hooks may transform the prompt, so initial admission follows its actual first committed user message instead of comparing it with the original text. An SDK-handled input pauses and releases ownership instead of waiting forever for a nonexistent run. A new explicit prompt drains a superseded Goal still preparing inside asynchronous SDK hooks; streaming prompts retain normal steering/queue behavior. If Stop/recovery happens before any user input was committed after the goal definition, explicit Resume submits the first user turn under a new charged dispatch, establishing its normal checkpoint. Before the goal definition is published, bounded private receipts fsync immutable SHA-256 file/image blobs, captured cwd, original paths and prompt file blocks. Files retain their type suffix; binary files and truncated text include an inspectable saved-copy reference. Image bytes are validated before persistence; events contain bounded paths/counts only, never base64. Resume checks blob sizes, hashes and image validity before charging or dispatching. Input consumption is an independent durable tombstone, so a new explicit user message can supersede a missing/corrupt receipt. The selected branch plus all persisted parent relationships prevent Rewind from replaying accepted input, even if a crash preceded that tombstone. A plain-text checkout may instead receive a fresh generated Resume command to establish its normal checkpoint; consumed attachments require a new explicit message. An already committed first input is never submitted again.

Automatic continuation uses a hidden `pith_goal_step_v1` custom message and the existing SDK `triggerTurn` lifecycle. It rejoins ChangeScopes without creating a user bubble or checkpoint, and reuses Continue's quoted partial-output context for an interrupted frontier; unfinished tool calls remain context, never executable evidence. Admission is reserved synchronously before asynchronous evidence/preparation. The captured managed session, cancellation generation, Plan gate and checkout run lease are rechecked before dispatch; active-chat navigation cannot retarget a run. Goal admission excludes other work reservations, including manual input preparation, reload and branch changes, and retries after reservations release. The initial input remains an initial user turn across this admission deferral rather than becoming a charged hidden continuation.

Only `agent_settled` or an app error ends ownership. Resolving `prompt()` or observing `agent_end` cannot launch a goal continuation. SDK retries, compaction and queued continuations stay within the owned run. The runtime waits for tasks, child runs, completion deliveries, questions, escalations and user queues before automatic dispatch or completion. Existing task/question/subagent notification owners deliver their results; the goal does not duplicate those wakes.

The Goal panel edits the current objective and acceptance criteria during execution, with stable criterion IDs and per-row revisions. Drafting does not affect running work. Save pins the goal ID and criteria revision instead of hot usage/status revisions, takes Plan's synchronous transition lock, stops and drains SDK/tools, children, commands and Rewind recording, then fsyncs the new definition and leaves the goal paused. Stop arriving during that drain cancels Save; no late definition can commit. Saving invalidates the overall completion candidate and Jev review. Changing the objective invalidates every criterion proof; changing one row invalidates only that proof. Unchanged rows retain their committed proofs. Pending questions and deliveries retain their paused owners for explicit Resume, and editing within Plan never changes permission mode or grants execution. Todo and lifetime accounting are retained. Removed IDs cannot be supplied as new rows, and new rows receive main-owned identities. The request remains the default single criterion. Criteria edits preserve the independent lifetime ledger.

`get_goal` exposes bounded committed result IDs, current criterion states and revisions. `update_goal(verify)` binds results to individual criteria; `complete` requires every criterion to have current proof, and `blocked` records a concrete external prerequisite. Prose and Todo bookkeeping cannot prove a criterion. Receipts are model-only and pin the current criteria revision. Main generates provenance references and only applies a committed successful top-level receipt. Both receipts and redundant state entries fold over the complete selected branch, including entries omitted from compacted provider context.

Each source observation is an fsynced private `pith_goal_evidence_v1` entry. It binds the committed source identity and full-result digest to observed full SHA-256 file versions. Reads and checks compare pre-execution and committed versions, refusing to bind old output to bytes changed in that interval. Delayed bash completion notices retain the originating command receipt’s observed versions and generation; delivery cannot rebind earlier success to changed files. File inspections/changes depend on their own file; checks conservatively depend on the observed workspace files and mutation generation. Latest results supersede older results for the same command, so a later failed check cannot disappear behind a passing receipt, including when it is omitted from the bounded view. Missing, pending, failed, superseded, unreadable or stale references cannot verify a row. File reads are bounded; the application does not infer arbitrary shell effects or independently establish every semantic claim. An actual new inspection may verify externally corrected contents without treating an old write as current evidence.

A committed completion receipt requests automatic application finalization at turn settlement. Tool/context guidance asks the model to report actual verified results, without promising later system review or settlement. **Completed** in the panel means application finalization has already finished; it does not enqueue another review. Jev review remains part of the existing workflow only when enabled.

Only a settled run with all criteria verified, no failed/unfinished checks, no unfinished Todo (including a retained cleared list), and drained work/questions/children/deliveries can complete. Final file validation holds the existing admission reservation and rechecks cancellation afterward, before changing state; it consumes no new dispatch. A late mutation, failure, outcome or user instruction invalidates the completion candidate. Unchanged criterion proofs stay inspectable and remain valid across repeated successful inspections; same-command failures still supersede passing checks. Opening the panel refreshes disk observations without starting execution. A completed goal whose evidence later becomes stale may be explicitly resumed or replaced by the next selected composer goal; explicit Pause, criterion edits and Rewind preserve the existing owner. Reopening, Rewind and recovery never append private observation/transition entries merely to inspect state. File-only Rewind pauses completed goals too, preserving exact conversation endpoints and usage.

When Jev workflow is enabled, its ordinary independent review receives all explicit criteria and their bound source IDs. Its completed state carries an identity for those exact criteria, proof states, source results and file versions. Changes to that identity cannot reuse an older review, and files are rechecked after the service response. Required proof sources omitted by the bounded service request cannot receive a completed review. Without Jev, structural/provenance validation does not claim an independent semantic audit. New meaningful results invalidate no-progress comparison; three settled runs with the same concrete evidence pause automatically. Todo rewrites or status prose alone do not count as progress.

Legacy prose-only completed/verifying records retain their goal identity and ledger but reopen paused for explicit evidence review. No legacy receipt can certify new criteria or create fresh allowance.

## Limits and recovery

The default is 20 automatic continuations, with a configurable range of 1–1000. The explicit initial prompt is excluded; manual Resume starts a counted continuation. A durable dispatch claim spends the attempt before execution. An interruption after claim does not refund it or replay it. Increasing a limit explicitly changes that branch's configured cap, never the pool's consumed amount. A fork inherits the original goal and spent pool, requiring explicit Resume; concurrent sessions claim the last shared slot atomically. Further forks preserve the original owner alias. Fork persistence fsyncs the new SDK file/directory and owner aliases before publishing the session. Missing/corrupt pool ownership cannot create fresh zero-usage allowance. A fresh independent pool requires explicit creation of a new goal ID. Goal quota errors are structured IPC results.

The optional Token budget shares SDK-reported input, output, cache-read and cache-write tokens across the goal's owned parent runs, child runs and Jev service requests. The collapsed allowance section separates parent, child and Jev totals. SDK standalone usage, compaction/branch summaries and tool-result billing are included; reasoning subsets and nested result metadata are not added again. Each new primary/child provider request and Jev request checks the shared pool first. Requests, summaries or background work already in flight can exceed the cap; this is a consumption limit rather than a reservation for predicted future usage.

`goals/accounting.ts` persists immutable source manifests and charge receipts under the original pool owner. Child source ownership freezes the originating Goal/parent dispatch, child session and run before execution; `pith_subagent_run` also retains the binding for explicit child continuation after the parent pauses or restarts. A fresh owned parent dispatch can assign a continued child to its current goal; otherwise continuation retains the child's preceding binding. Ordinary unowned work and Settings connection probes do not acquire a Goal charge. The child ceiling, Plan restrictions and nonrecursive Jev workflow remain unchanged.

For each child provider request, a durable claim retains the pre-request SDK entry IDs and request sequence. Reported response usage is fsynced before forwarding completion to the SDK and charged with that request identity. The corresponding committed assistant entry reconciles to the same identity; independent SDK summary/tool/usage entries retain their own IDs. A known response survives Stop even if the SDK discards its message. Child settlement fsyncs the full file, reconciles all requests and closes the source before disposal; a closed child can later be deleted without losing charges. Bounded teardown that cannot settle retains an unresolved source. On restart, recovery reads private receipts and SDK files without executing the child or changing the selected leaf.

Jev uses the official client with retries disabled. Ownership is captured before credential lookup, but the source is claimed only immediately before transport dispatch. Reported usage is persisted before cancellation and answer validation, so a cancelled or semantically invalid billed response still counts. Local request IDs, tool-call/trace IDs, the exact child run ID for child-owned Jev calls and available provider request IDs retain provenance; credentials and prompt payloads are absent from receipts. All immutable receipts are written before the locked shared-pool debit. A kill between these writes is repaired idempotently from the receipt. Fork aliases point to this same journal/pool; Rewind never refunds spending or replays a claim.

An actually dispatched request without a verifiable provider/SDK usage receipt remains **unconfirmed accounting**, rather than a fabricated zero fee. SDK-generated zero-usage abort/error placeholders and unrelated later summary/tool fees cannot settle it. The panel reports the unresolved count; automated Goal execution, explicit Goal Resume and further attributed child/Jev dispatch refuse until accounting can be reconciled. Increasing limits does not clear the unresolved source or spent amount. Known receipts can reconcile on restart; the application cannot recover usage a remote provider never reported. Missing/corrupt source, charge or request records also fail closed. Historical work created before these attribution records existed is not estimated or retroactively assigned from message prose.

Reopening an active/verifying goal pauses it as interrupted. Claimed/started ledger dispatches are reconciled and cleared, never replayed. Resume reuses committed context and Todo, requires available allowance, and creates a new dispatch. Stop or Pause invalidates goal preparation before aborting the SDK, recalling queues, pausing notifications and stopping child/process/debug owners. Quit closes goals before teardown and never starts another wake. An ordinary explicit user prompt can still run in a paused-goal conversation; it does not resume the goal.

Entering Plan takes the synchronous transition lock before cancelling/draining a preparing goal wake and pauses the goal. Other already admitted work makes the mode change refuse synchronously; its next asynchronous boundary must not be interrupted by a transient Plan lock. Leaving Plan does not resume the goal. Goal execution cannot unseal a submission or approve a plan; the existing exact approval flow remains required. Plan exposes only the app-owned read tool, with goal status mutation absent. Child ceilings forbid both goal tools, and model-only update cannot be invoked through codemode.

Conversation Rewind, Resend and recovery invalidate goal wakes before navigation. The selected branch is folded again after navigation, historical live state is paused, and lifetime accounting is retained. File-only Rewind also pauses the current goal so automatic work cannot immediately overwrite restored files. Goal mutations cannot append entries while a branch operation, pending Rewind crash recovery or Plan transition owns admission. Rejected prompt/Continue/Resend requests cannot mutate verification before obtaining admission. An accepted Resend grants ordinary manual answer wakes without resuming the restored Goal. Checkout leases continue to fence process/tool/child work.

## Verification

`goals` uses the real pinned SDK with an isolated fake provider: committed receipts, Todo completion gating, hidden continuations, request and run caps, explicit Resume, preserved interrupted context and async answers, Stop during preparation, Plan sealing, conversation/file Rewind and transaction recovery, independent metadata revisions, crash reconciliation and corrupt-ledger refusal. Its Jev workflow fixture checks router/review service charges independently from primary SDK tokens. Deferred barriers exercise Resume/Pause/End/Stop during Rewind, Plan drainage, manual preparation, transformed/handled/delayed SDK inputs, preserved image/file attachments and Resend/manual answer wakes.

`goal-evidence` adds per-row revision edits, retained unchanged proofs, rejected Todo/unknown/stale references, external and in-execution file changes, latest failing checks, plausible false completion claims, final-validation Stop/Plan races, compaction, file-only Rewind, legacy migration and restart without endpoint/accounting changes. The Jev fixture verifies criteria payloads and rejects reuse of a pre-edit review.

`goal-definition` exercises live SDK/tool drainage, stale definition/receipt refusal, Stop winning Save, Plan/Rewind/manual-admission fencing, preserved Todo/usage and capture cancellation. `goal-fork` verifies shared atomic spending, independent dispatch scopes, multi-hop owner aliases, Rewind and unavailable pools.

`goal-accounting` drives real managed SDK children and the official Jev client against offline transport. It checks parent/child tool Jev attribution, child Resume/deletion, full-branch Rewind, Fork shared caps, cache/summary/tool/standalone fees, cancellation/invalid-response usage and unavailable-accounting refusal. Live background-child barriers verify Pause/Stop with late paid responses, Plan admission and explicit Resume. Aborted zero placeholders and unrelated later fees cannot conceal an unknown request; verifiable late receipts reconcile without granting an automatic wake. `goal-accounting-recovery` sends actual SIGKILL at ten independent child/Jev claim, receipt, SDK commit, pool debit, child deletion and Fork boundaries; each is reopened twice with no provider calls, no accepted-turn replay and no duplicate fees.

`goal-recovery` kills an owned OS process with SIGKILL after definition, initial/charged claim, user/usage/receipt/final-state commits, explicit End, Plan entry, Stop, Rewind journal commitment, disk-write failure, fork publication and lock acquisition. Restart calls no provider, preserves the exact leaf and accepted messages, pauses unfinished work and bills committed charges once. Immutable pending files/images survive deleted originals; binary and truncated text remain inspectable. Tampered/missing input cannot spend or dispatch, and missing/corrupt accounting never becomes zero usage. A killed lock owner refuses execution until the stale-lock boundary, then reconciles once.

`goals-ui` uses Electron, real Composer/beUI and fake typed IPC to verify default-off presentation, bottom-only selection without execution, localized placeholder changes, the Goal tab appearing after send without auto-opening, the exact submitted user message as current goal, immediate draft release and continued editing, duplicate/invalid/refused starts, live objective/criterion editing, collapsed proof/allowance controls and independent fee totals, unresolved-accounting Resume refusal, one acceptance view, completed-goal restart and durable End presentation, retained edits on refusal, pause/resume/limit/End actions, Plan disabling, Escape ownership, stable overlay geometry, late-response session identity and all three locales. `new-session-project` uses the complete built renderer to verify selection preserves landing-page geometry, project controls, backdrop, editor identity and drafts in project, projectless and narrow layouts. Adjacent Plan, Todo, SDK boundary, lifecycle, replay, bash, ask-user, subagent, Jev and Rewind suites cover shared owners. Offline fixtures verify ownership and reported-usage accounting, not real-provider billing accuracy or model completion quality. The process-kill matrices run on POSIX; they do not establish Windows process/locking behavior. See [next steps](goals-next-steps.md).
