# Native session goals

The task strip's **Goal** tab owns one current goal for each ordinary conversation. The user supplies an objective, acceptance criteria and limits. The existing Todo list remains the task source; there is no second task list. A completed or cancelled goal may be replaced by an explicitly created new goal. Children and scheduled-run conversations cannot create or run goals.

## Ownership and persistence

`src/shared/goal.ts` owns IPC data. `main/pi/goals/runtime.ts` owns state, SDK settlement and continuation admission. `goals/tools.ts` registers `get_goal` and model-only `update_goal`; the latter returns a receipt, and only a committed successful top-level result changes state. Context guidance is request-only and survives compaction/reload through the session's owned loader. `GoalPanel` composes beUI inside the existing `SessionTasks` overlay.

Goal definitions, limits and explicit transitions are private `pith_goal_v1` entries on the complete selected SDK branch. Successful `update_goal` receipts also fold into branch state, covering a crash between result persistence and its redundant state record. Explicit transitions use the existing session append/fsync boundary. Restoration adds an effective execution pause without appending to the SDK branch: reviewed preview leaves, file-only restores and crash journals must retain their exact endpoints. Reopening an active branch always pauses it; only explicit Resume can grant execution again. Goal metadata has a per-session revision independent of transcript `eventSequence`; null updates are revisioned tombstones, and late action responses stay with their originating conversation.

The independent `<userData>/goals/` ledger is keyed by session ID and goal ID. Locked atomic replacement, file fsync and directory fsync protect its usage, billed-entry identities, progress fingerprint and dispatch claim. It is outside conversation branches: Rewind, Resume and ordinary branch restoration cannot refund used allowance. An unavailable, missing or malformed existing ledger stops automatic execution and exposes unavailable accounting. Goal entries alone never grant execution or create a replacement zero-usage ledger.

## Lifecycle

The explicit Start operation sends an ordinary user prompt, so Rewind captures its normal before-turn checkpoint. Automatic continuation uses a hidden `pith_goal_step_v1` custom message and the existing SDK `triggerTurn` lifecycle. It rejoins ChangeScopes without creating a user bubble or checkpoint, and reuses Continue's quoted partial-output context for an interrupted frontier; unfinished tool calls remain context, never executable evidence. Admission is reserved synchronously before asynchronous evidence/preparation. The captured managed session, cancellation generation, Plan gate and checkout run lease are rechecked before dispatch; active-chat navigation cannot retarget a run.

Only `agent_settled` or an app error ends ownership. Resolving `prompt()` or observing `agent_end` cannot launch a goal continuation. SDK retries, compaction and queued continuations stay within the owned run. The runtime waits for tasks, child runs, completion deliveries, questions, escalations and user queues before automatic dispatch or completion. Existing task/question/subagent notification owners deliver their results; the goal does not duplicate those wakes.

`update_goal(complete)` requests verification. Main completes only after the run settles, pending work drains and the existing Todo list has no pending/in-progress items. A later mutation, failed tool result, background outcome or new user request invalidates the candidate and requires fresh evidence. When Jev workflow is enabled, it must finish its ordinary review; a paused review pauses the goal. Without Jev, completion evidence is the model's explicit receipt plus these structural checks, not an independent semantic audit of every criterion. `update_goal(blocked)` records the external prerequisite and requires user Resume. New meaningful results invalidate no-progress comparison; three settled runs with the same concrete evidence pause automatically. Todo rewrites or status prose alone do not count as progress.

## Limits and recovery

The default is 20 automatic continuations, with a configurable range of 1–1000. The explicit initial prompt is excluded; manual Resume starts a counted continuation. A durable dispatch claim spends the attempt before execution. An interruption after claim does not refund it or replay it. Increasing a limit explicitly changes the cap, never the consumed amount. Goal quota errors are structured IPC results.

The optional Token budget counts SDK-reported input, output, cache-read and cache-write tokens in the goal's owned parent-session runs. It includes standalone usage, compaction/branch summaries and tool-result billing reported in that session, without counting nested usage twice. It does not estimate future requests or claim unreported/independent child or Jev-service billing. Every primary provider request, including an SDK/Jev continuation within a run, checks the budget first. A request already in flight can exceed the cap; summarization or background work already in flight also cannot be preempted into an exact token limit. The UI states this scope. Usage is keyed by persisted entry ID across all branches, so rewind cannot erase spending. An interrupted open run is reconciled from committed entries once.

Reopening an active/verifying goal pauses it as interrupted. Claimed/started ledger dispatches are reconciled and cleared, never replayed. Resume reuses committed context and Todo, requires available allowance, and creates a new dispatch. Stop or Pause invalidates goal preparation before aborting the SDK, recalling queues, pausing notifications and stopping child/process/debug owners. Quit closes goals before teardown and never starts another wake. An ordinary explicit user prompt can still run in a paused-goal conversation; it does not resume the goal.

Entering Plan cancels any preparing goal wake and pauses the goal. Leaving Plan does not resume it. Goal execution cannot unseal a submission or approve a plan; the existing exact approval flow remains required. Plan exposes only the app-owned read tool, with goal status mutation absent. Child ceilings forbid both goal tools, and model-only update cannot be invoked through codemode.

Conversation Rewind, Resend and recovery invalidate goal wakes before navigation. The selected branch is folded again after navigation, historical live state is paused, and lifetime accounting is retained. File-only Rewind also pauses the current goal so automatic work cannot immediately overwrite restored files. Checkout leases continue to fence process/tool/child work.

## Verification

`goals` uses the real pinned SDK with an isolated fake provider: committed receipts, Todo completion gating, hidden continuations, request and run caps, explicit Resume, preserved interrupted context and async answers, Stop during preparation, Plan sealing, conversation/file Rewind and transaction recovery, independent metadata revisions, crash reconciliation and corrupt-ledger refusal. `goals-ui` uses Electron, real beUI and fake typed IPC to verify create/pause/resume/cancel/limit actions, Plan disabling, Escape ownership, stable overlay geometry, late-response session identity and all three locales. Adjacent Plan, Todo, SDK boundary, lifecycle, replay, bash, ask-user, subagent, Jev and Rewind suites cover shared owners. Offline fixtures do not establish real-model goal completion quality.
