# Native session goals

Each ordinary conversation owns one current goal. New conversations start with Goal mode off and no Goal tab in the task strip. Selecting **Goal mode** from the composer's **+** menu shows its bottom mode control and opens the task strip's Goal panel, without creating a goal or granting execution. The user supplies the objective by sending the composer message; optional acceptance criteria and limits live in the panel. Without separate criteria, verification targets the requested outcome in that message. The existing Todo list remains the task source; there is no second task list. Children and scheduled-run conversations cannot create or run goals.

Composer intent/draft/open revision belong to the renderer's per-conversation store, separately from native Goal revisions. Creation pins the native session, goal ID and revision and returns after recording/admitting work; it does not await the SDK run. The editor releases its text/attachments immediately and remains editable while IPC is pending. Pending admission prevents duplicate submission. A refusal restores the old draft without overwriting newer input; late receipts update only their originating conversation. Successfully used optional criteria are cleared for the next goal.

The panel's bottom **End** button cancels a nonterminal goal through the ordinary Stop path, then hides the Goal panel/tab and composer mode control. Goal records and lifetime accounting remain. Ending an unstarted, completed or cancelled mode only changes presentation. Pause keeps the mode visible and requires explicit Resume. Messages sent while an unfinished goal already exists are ordinary user instructions: they neither replace the objective nor implicitly resume a paused goal. After completion/End, another explicitly selected send can create a new goal. A restored unfinished goal remains discoverable but execution is paused.

## Ownership and persistence

`src/shared/goal.ts` owns IPC data. `main/pi/goals/runtime.ts` owns state, SDK settlement and continuation admission. `goals/tools.ts` registers `get_goal` and model-only `update_goal`; the latter returns a receipt, and only a committed successful top-level result changes state. Context guidance is request-only and survives compaction/reload through the session's owned loader. `GoalPanel` composes beUI inside the existing `SessionTasks` overlay.

Goal definitions, limits and explicit transitions are private `pith_goal_v1` entries on the complete selected SDK branch. Successful `update_goal` receipts also fold into branch state, covering a crash between result persistence and its redundant state record. Explicit transitions use the existing session append/fsync boundary. Restoration adds an effective execution pause without appending to the SDK branch: reviewed preview leaves, file-only restores and crash journals must retain their exact endpoints. Reopening an active branch always pauses it; only explicit Resume can grant execution again. Goal metadata has a per-session revision independent of transcript `eventSequence`; null updates are revisioned tombstones, and late action responses stay with their originating conversation.

The independent `<userData>/goals/` ledger is keyed by session ID and goal ID. Locked atomic replacement, file fsync and directory fsync protect its usage, billed-entry identities, progress fingerprint and dispatch claim. It is outside conversation branches: Rewind, Resume and ordinary branch restoration cannot refund used allowance. An unavailable, missing or malformed existing ledger stops automatic execution and exposes unavailable accounting. Goal entries alone never grant execution or create a replacement zero-usage ledger.

## Lifecycle

The initial composer send becomes an ordinary user prompt, so Rewind captures its normal before-turn checkpoint. Image attachments follow SDK validation/normalization; files are read using the captured conversation's cwd. Input hooks may transform the prompt, so initial admission follows its actual first committed user message instead of comparing it with the original text. An SDK-handled input pauses and releases ownership instead of waiting forever for a nonexistent run. A new explicit prompt drains a superseded Goal still preparing inside asynchronous SDK hooks; streaming prompts retain normal steering/queue behavior. If Stop/recovery happens before any user input was committed after the goal definition, explicit Resume submits the first user turn under a new charged dispatch, establishing its normal checkpoint. In-process pauses retain pending attachments; durable pending-attachment receipts are part of the next-step recovery work. An already committed first input is never submitted again.

Automatic continuation uses a hidden `pith_goal_step_v1` custom message and the existing SDK `triggerTurn` lifecycle. It rejoins ChangeScopes without creating a user bubble or checkpoint, and reuses Continue's quoted partial-output context for an interrupted frontier; unfinished tool calls remain context, never executable evidence. Admission is reserved synchronously before asynchronous evidence/preparation. The captured managed session, cancellation generation, Plan gate and checkout run lease are rechecked before dispatch; active-chat navigation cannot retarget a run. Goal admission excludes other work reservations, including manual input preparation, reload and branch changes, and retries after reservations release. The initial input remains an initial user turn across this admission deferral rather than becoming a charged hidden continuation.

Only `agent_settled` or an app error ends ownership. Resolving `prompt()` or observing `agent_end` cannot launch a goal continuation. SDK retries, compaction and queued continuations stay within the owned run. The runtime waits for tasks, child runs, completion deliveries, questions, escalations and user queues before automatic dispatch or completion. Existing task/question/subagent notification owners deliver their results; the goal does not duplicate those wakes.

`update_goal(complete)` requests verification. Main completes only after the run settles, pending work drains and the existing Todo list has no pending/in-progress items. A later mutation, failed tool result, background outcome or new user request invalidates the candidate and requires fresh evidence. When Jev workflow is enabled, it must finish its ordinary review; a paused review pauses the goal. Without Jev, completion evidence is the model's explicit receipt plus these structural checks, not an independent semantic audit of every criterion. `update_goal(blocked)` records the external prerequisite and requires user Resume. New meaningful results invalidate no-progress comparison; three settled runs with the same concrete evidence pause automatically. Todo rewrites or status prose alone do not count as progress.

## Limits and recovery

The default is 20 automatic continuations, with a configurable range of 1–1000. The explicit initial prompt is excluded; manual Resume starts a counted continuation. A durable dispatch claim spends the attempt before execution. An interruption after claim does not refund it or replay it. Increasing a limit explicitly changes the cap, never the consumed amount. Goal quota errors are structured IPC results.

The optional Token budget counts SDK-reported input, output, cache-read and cache-write tokens in the goal's owned parent-session runs. It includes standalone usage, compaction/branch summaries and tool-result billing reported in that session, without counting nested usage twice. It does not estimate future requests or claim unreported/independent child or Jev-service billing. Every primary provider request, including an SDK/Jev continuation within a run, checks the budget first. A request already in flight can exceed the cap; summarization or background work already in flight also cannot be preempted into an exact token limit. The UI states this scope. Usage is keyed by persisted entry ID across all branches, so rewind cannot erase spending. An interrupted open run is reconciled from committed entries once.

Reopening an active/verifying goal pauses it as interrupted. Claimed/started ledger dispatches are reconciled and cleared, never replayed. Resume reuses committed context and Todo, requires available allowance, and creates a new dispatch. Stop or Pause invalidates goal preparation before aborting the SDK, recalling queues, pausing notifications and stopping child/process/debug owners. Quit closes goals before teardown and never starts another wake. An ordinary explicit user prompt can still run in a paused-goal conversation; it does not resume the goal.

Entering Plan takes the synchronous transition lock before cancelling/draining a preparing goal wake and pauses the goal. Other already admitted work makes the mode change refuse synchronously; its next asynchronous boundary must not be interrupted by a transient Plan lock. Leaving Plan does not resume the goal. Goal execution cannot unseal a submission or approve a plan; the existing exact approval flow remains required. Plan exposes only the app-owned read tool, with goal status mutation absent. Child ceilings forbid both goal tools, and model-only update cannot be invoked through codemode.

Conversation Rewind, Resend and recovery invalidate goal wakes before navigation. The selected branch is folded again after navigation, historical live state is paused, and lifetime accounting is retained. File-only Rewind also pauses the current goal so automatic work cannot immediately overwrite restored files. Pause/End/Resume cannot append Goal entries while a branch operation or Plan transition owns admission. Rejected prompt/Continue/Resend requests cannot mutate verification before obtaining admission. An accepted Resend grants ordinary manual answer wakes without resuming the restored Goal. Checkout leases continue to fence process/tool/child work.

## Verification

`goals` uses the real pinned SDK with an isolated fake provider: committed receipts, Todo completion gating, hidden continuations, request and run caps, explicit Resume, preserved interrupted context and async answers, Stop during preparation, Plan sealing, conversation/file Rewind and transaction recovery, independent metadata revisions, crash reconciliation and corrupt-ledger refusal. Deferred barriers exercise Resume/Pause/End/Stop during Rewind, Plan drainage, manual preparation, transformed/handled/delayed SDK inputs, preserved image/file attachments and Resend/manual answer wakes.

`goals-ui` uses Electron, real Composer/beUI and fake typed IPC to verify default-off presentation, selection without execution, send-to-start, immediate draft release and continued editing, duplicate/invalid/refused starts, pause/resume/limit/End actions, Plan disabling, Escape ownership, stable overlay geometry, late-response session identity and all three locales. Adjacent Plan, Todo, SDK boundary, lifecycle, replay, bash, ask-user, subagent, Jev and Rewind suites cover shared owners. Offline fixtures do not establish real-model completion quality or replace OS process-kill testing at every persistence boundary. See [next steps](goals-next-steps.md).
