# Native Jev integration

Settings → Jev has three exclusive modes: **Off** (default), **Provide tool**, and **Jev workflow**. Tool mode exposes `jev_decide` with individual Choice, Score and Noul switches. Workflow mode runs app-owned routing and verification for parent tasks; these switches apply only to tool mode. Save a TypeSafe API key and test the connection. A primary model provider is still required. Legacy `enabled: true` settings migrate to tool mode, never to mandatory workflow.

The Electron main process uses the official [`@typesafe-ai/sdk`](https://docs.typesafe.ai/sdk/javascript), pinned to 0.6.0, with model `jev-1.13.0`. No Pi extension or skill installation is required. The tool guidelines follow the [official TypeSafe skill](https://github.com/typesafe-ai/skills/blob/main/skills/typesafe-ai/SKILL.md): atomic questions, complete instructions (question IDs are invisible to Jev), independent batches, concrete score levels, appropriate no-match choices, and explicit handling of uncertainty. There is no universal confidence threshold. Automatic continuation is available only in the explicitly selected workflow mode and continues without a fixed correction, primary-request or total-duration cap.

## Optional global skill

The official `typesafe-ai/skills` → `skills/typesafe-ai` skill can be installed under `<Pi agent directory>/skills/typesafe-ai`. The local installation uses upstream commit `65a39f393687675ce170e6094757de20370365b9`, retains the MIT license and original text, and adds a marked Pi bridge. New Pi sessions discover it automatically; existing sessions can use `/reload`. Explicit invocation is `/skill:typesafe-ai`.

The bridge distinguishes a native judgment in the current task from implementing the TypeSafe SDK in a user's project. Native calls use `jev_decide` and the app's settings; SDK development follows the original live-docs workflow. The tool references the skill only when it is listed among available skills, so installations without the skill remain self-contained. The reference gives native parameter limits, working evidence-check/ranking examples and error handling. It never supplies credentials or expands a subagent's tool ceiling.

`resources/jev/pi-app.md` is the maintained native reference. After installing or reviewing an upstream update, apply the bridge with:

```sh
node scripts/adapt-typesafe-skill.mjs ~/.pi/agent/skills/typesafe-ai
node scripts/check-jev-skill.mjs ~/.pi/agent/skills/typesafe-ai
```

The adapter preserves unrelated edits and keeps the first pre-adaptation body in `.pi-app-original.md`. It performs no installation, network access or credential reads. Upstream updates should be reviewed against that original before reapplying the bridge; they are never downloaded silently on app startup.

## Settings and credentials

- `AppSettings.jev` stores a three-value mode and three capability booleans. Updates immediately rebuild existing sessions' active tool sets and prompts; execution also reads live flags.
- A saved key lives in `<Pi agent directory>/jev-auth.json` (normally `~/.pi/agent/jev-auth.json`), with mode `0600` and atomic replacement. It is a local plaintext credential file, following Pi's local credential convention, not an OS keychain. It is never returned through settings IPC or stored in localStorage.
- Saved credentials take precedence over `TYPESAFE_API_KEY`; removing the saved key falls back to that environment variable. An unreadable credential file fails visibly rather than silently using a different account.
- The connection test uses one fixed synthetic bug report and all three question types, even while the model-facing tool is off. It consumes API quota, and never reads workspace files or conversation history.

## Request and lifecycle contract

`jev_decide` accepts `state` (relevant text or serialized JSON) and a map of up to 32 independent questions. A Choice supplies 2–32 named options; a Score supplies 2–10 ordered descriptions; a Noul supplies a yes/no question with optional `true`/`false` criteria (both descriptions required when supplied). The total serialized input is limited to 64 KiB. Only the supplied input is sent to TypeSafe. The app materializes the owned Jev definition's current description when applying active tools, because SDK registration caches descriptions; the prompt snippet deliberately contains no cached capability list.

The service pins the official HTTPS endpoint, disables SDK request logging and retries, uses a 10-second request deadline and caps application-wide concurrency at four. Stop, session disposal, application shutdown and settings changes cancel in-flight requests. A request checks lifecycle admission again after asynchronous credential lookup. Responses are validated against the requested question IDs, types, probability ranges and options. Only verified fields are persisted in tool results; failures expose stable codes, with renderer translations, never SDK error bodies or credential values.

Plan Mode permits only the captured app-owned tool definition. It performs no project mutations and grants no execution authority. A subagent can use Jev only when its profile and its parent's active tools included it at dispatch; enabling Jev later never widens that frozen ceiling. The native tool does not require extension loading.

## Verification

`node scripts/check-jev.mjs` exercises validation, transport errors, cancellation, credentials, real SDK registration, live settings, Plan admission and child ceilings using an isolated temporary profile. It also covers mandatory routing, correction of advice-only responses to action requests, 30 corrections with actual file progress, same-target and A/B/A loop detection, Unicode request budgets, paged judgment history, selected-branch detail lookup, prefix preservation, Plan workflow bypass, pending background work, restart recovery, stale IPC snapshots, and mode changes. Set `PI_JEV_LIVE_KEY_FILE` to a private file containing a key, or `PI_JEV_LIVE_SAVED_KEY_FILE` to an existing saved Jev credential file, for the optional real API probe and Router → mocked executor → Verifier checks. The latter includes real temporary-file modification and a real shell assertion. The script never prints the key.

`node scripts/check-jev-evidence.mjs` checks retained patches and command outcomes after inspection noise, current file versions, stale checks, temporary harnesses, child writes from failed runs, duplicate child completion delivery, research progress, and omitted images. Its optional `PI_JEV_LIVE_SAVED_KEY_FILE` tests use synthetic icon-change evidence: completed change, unsupported success with no change, and externally reverted code with stale passing checks.

`node scripts/check-settings-tabs.mjs` covers the Jev page, secret input, saving/removing, connection success/failure, draft retention, and live English/Chinese translations. `PI_JEV_SCREENSHOT_DIR` optionally retains light/dark screenshots. Also run typecheck/build and Plan, lifecycle, tool-catalog and icon regressions when changing shared session wiring.

`node scripts/check-jev-skill.mjs` checks discovery, idempotent adaptation, upstream/local-edit preservation, skill visibility and all reference examples against the native schema. Pass an installed skill directory to verify that installation too. Proposed next steps are in [the integration roadmap](jev-roadmap.md); that document distinguishes the current WIP from future work.


## Mandatory workflow — WIP v1

`main/pi/jev/workflow.ts` wraps public Pi Agent context, streaming, tool-admission and completion hooks. A skill or a primary-model tool call cannot opt out of these hooks. This controls the app's model loop; trusted extensions still execute in the Electron host and this is not a plugin sandbox.

1. Before the first primary-model request, Router selects `respond` (explicit explanation/conversation), `inspect` (investigate the project), or `act` (perform requested work). These are guidance, not additional permission gates: a wrong `respond` must not prevent the executor from reading files. A conservative explicit-action guard corrects unmistakable coding imperatives to `act`. Jev selects a workflow, not a specific subagent profile.
2. The main model executes under the existing active tools, Plan/sandbox gates and child ceilings. Children run their dispatched tasks without a recursive Jev controller. Missing project context is a reason to gather evidence, not a reason to substitute advice for a requested change.
3. At an ordinary final response, `evidence.ts` folds the complete current user turn on the selected branch into a bounded ledger. Actual edit patches, current changed-file text, child changes and normalized command exit/output survive later read/grep noise. Retries of the same command replace its old outcome. Inspections and checks retain their file-version associations; obsolete success text is withheld from current proof, with explicit stale markers and references. The submitted state also includes the request, two brief preceding conversational excerpts, answer, omitted counts and previous review targets. An explicit action request without any project tool evidence cannot be certified complete; a premature `complete` is corrected to implementation. Todo bookkeeping alone is not evidence.
4. `review.ts` supplies ONE Choice question: `complete`, `blocked`, `uncertain`, or a concrete original-request/file/failure target. This avoids inconsistent independent completion/gap answers. A selected target maps to `continue`, `verify` or `retry`; it appends one hidden instruction carrying the original requirement, target and existing passing checks. A symbol-wiring change does not acquire a screenshot, pixel-comparison or packaging requirement just because the model mentions it. `blocked` and `uncertain` are visible unresolved states, never successful completion.
5. Each issued target is persisted with its relevant code/evidence fingerprint. Repeating that target on unchanged code stops automatic repetition with `no_progress`; it does not certify success. The detector compares all previous targets, so A/B/A cannot reset it. Repeated checks, new timestamps and temporary verification harnesses do not advance a file-verification target. Actual relevant file changes, including shell/external changes to known paths, can advance it. Research without file changes uses novel source-result text. This is a convergence guard at final-response boundaries, not a proof that every model tool call is useful. There is no correction-count, primary-request-count or total-duration limit. The former two-round / 24-request / ten-minute limits were WIP app policy, not Jev restrictions, and are removed.
6. Stop, mode changes, missing credentials, invalid responses and service failures still interrupt the workflow. A mandatory judgment that could not be obtained must not be silently marked successful. SDK continuations and completion wakes cannot bypass that interruption. While paused, the SDK's `hasQueuedMessages` probe reports false without clearing the queues; otherwise its outer loop spins on a declined `continue()`. An explicit extension boundary continuation also ends the outer run through non-awaited `session.abort()` (awaiting that run's own idle promise would deadlock). A new message starts a fresh epoch; Continue can resume an interrupted frontier while retaining prior target attempts. Recovery does not automatically replay work. The service's individual-request deadline and concurrency bound are transport controls, not task-duration limits.

Evidence is bounded to 48 retained items and a 33 KB item budget before final request fitting; the request is capped below the native 64 KiB limit. File hashing covers up to 64 known paths, prioritizing changed files, and reads at most 2 MiB per file; unavailable or larger files remain explicit. `pith_jev_evidence_v2` records version associations and `pith_jev_progress_v2` records issued targets, both outside model context. Unknown shell-written paths, truncated evidence and semantic judgments remain limitations. The controller cannot guarantee against every false acceptance or every possible semantic loop; it prevents the observed repeated-verification pattern without an arbitrary task budget.

Pending processes, subagents and user questions prevent completion certification. Their existing completion notifications resume the same workflow. The workflow controller stays inactive during Plan Mode: a planning or revision turn uses the plan submission contract, without Jev's implementation route or verifier. Stop/disposal cancel owned requests. A settings-mode change cancels an active workflow run; new requests use the selected mode. The global optional skill has been adapted to avoid duplicate control loops.

The task-strip Jev button opens the shared task overlay without moving the transcript. Only one task/Jev panel is open at a time; Escape closes it before the run stop handler and returns focus to the button. The panel shows phase, selected workflow, correction count, primary request count, and separate normalized input/output/cache-read/cache-write/Jev token counters. These counters cover the **parent session**, not subagent totals or summarization calls. Branch-owned `pith_jev_workflow_v1` metadata contains only status/counters; reopening an interrupted run shows paused, never replays it. Events have an independent revision and never advance transcript `eventSequence`.

Each new judgment persists its submitted redacted text/questions and actual typed response (model, usage, latency, probabilities and confidence) in separate `pith_jev_judgment_v1` custom entries, outside model context. Raw and effective decisions are shown separately when the app corrects routing or completion. Expanded details include the selected concrete target and its evidence references. Failed calls retain safe error codes. History is paged (30 summaries per request); full evidence loads only on expansion. Both read the complete selected branch, so details survive compaction/reopen and disappear from the active view after rewind. Old status-only records cannot reconstruct missing input/output. Interrupted requests are labeled as such, never left looking active after restart.

## Context, privacy and caching

Workflow mode automatically sends bounded task, patch, changed-file and tool-result text excerpts to TypeSafe (disclosed beside the mode control). It does not send image bytes, reasoning blocks, arbitrary tool-detail objects, or entire conversations. Only recognized patch/child-write/command fields are extracted from tool details. Common API-key/authorization/password patterns are redacted best-effort; this is not a general secret detector. Excerpts include their beginning and end, truncation markers and omitted-result counts. Text-only and truncated evidence limits the verifier's judgment quality. The router is told explicitly when images were omitted. The vision-capable primary model retains the original attachment and reads project files through tools; Jev receives text excerpts and the proposed answer, not an independent visual observation. It must not certify pixel-level correctness from an executor's unsupported claim. A dedicated source-linked visual evidence step remains future work.

Router guidance is a hidden custom message appended **once**, preserved in the durable branch, agent state and current loop context. Corrections also append hidden messages. Neither creates a real user turn or Rewind checkpoint. The system prompt and tool definitions are unchanged between stages; previous messages are not rewritten. This preserves eligible cache prefixes, including the earlier workflow guidance. Turning the mode off removes workflow guidance from the request view; an explicit mode change can therefore reduce cache reuse. Ordinary compaction/model changes/provider TTLs and cache breakpoints still apply.

Fewer unnecessary investigations, delegations or repair attempts can reduce primary-model usage; routing alone does not shorten the full tool schema or primary context. Jev calls and extra verifier-requested rounds add latency and tokens, so there is **no demonstrated net saving yet**. Compare completed tasks at equal quality, including parent and child uncached input, output, cache reads/writes, Jev tokens, time and failed/retried work. Cache reuse saves recomputation and cost according to provider rules; it is not the same as removing input tokens.

Official references: [OpenAI prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching) and [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching). Prefix equality is necessary; an eligible cached breakpoint must also exist. This WIP preserves context structure without modifying provider-specific cache policy.

Typecheck/build and the Jev, settings/task-panel, Plan, Continue, session lifecycle/persistence, background task and subagent checks passed. Real TypeSafe API checks cover the fixed probe, an ordinary reply and a synthetic icon change with real file and shell tools.
