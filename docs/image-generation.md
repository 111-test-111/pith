# Image generation

The first-party `image` tool generates or edits images through the configured OpenRouter account. It is registered with each managed session and exposed directly to the model, because its persisted tool result owns billing and committed file receipts. Plan refuses it before sending a request. Child sessions retain their frozen tool ceilings.

`main/pi/image.ts` owns admission, input validation, protocol selection and result receipts. `image-protocol.ts` implements the native OpenRouter image API and adapts the SDK chat image API. `shared/image.ts` owns the schema constants and durable result parser. See OpenRouter's [image guide](https://openrouter.ai/docs/guides/overview/multimodal/image-generation) and [endpoint reference](https://openrouter.ai/docs/api/api-reference/images/generate-an-image) for provider capabilities; individual models may accept different controls.

## Global image skill

The app ships [openrouter-image](../resources/skills/openrouter-image/SKILL.md) with researched [model selection and endpoint limits](../resources/skills/openrouter-image/references/models.md) and [parameter combinations](../resources/skills/openrouter-image/references/parameters.md), checked 2026-10-04. Its general recommendations prefer GPT Image 2.5 Flare for everyday generation/edits and Sunburst for demanding edits, while respecting named models, budgets and specialized output requirements. The tool's omitted-model default remains Klein. Tool descriptions require reading the skill before an image call and link its installed absolute path; field descriptions leave provider-specific examples and combinations to the skill. Existing schema enums remain app-wide bounds, not per-model capability claims. This is model guidance, not a runtime proof that a model read the skill.

`image-skill.ts` installs the shipped files into Pi's global `<getAgentDir()>/skills/openrouter-image/` at app startup, normally `~/.pi/agent/skills/openrouter-image/`; the SDK's agent-directory override selects another location. Development uses `resources/skills/`; packaging copies that source to the application's external resources. The live SDK loader receives the installed skill path for every managed session, including projectless and child/scheduled sessions, and deduplicates it with ordinary global discovery. Explicit invocation and reload behavior remain available. Settings' existing skill preview/toggle acts on the writable global copy. Disabling automatic model invocation hides its discovery entry; the image tool retains the absolute read path and resolves supporting references beside it because using the tool still requires this guidance.

Updates refresh only content matching the prior shipped hash (ignoring the invocation toggle on `SKILL.md`), retain the invocation preference and preserve locally edited bodies/references. A missing or invalid baseline never authorizes overwriting local content. Installation is confined to the `openrouter-image/` directory and makes no provider request.

## Requests and billing

Omitting `protocol` selects `auto`: try the remembered protocol (native initially), then the other endpoint only on a recognized protocol mismatch. Authentication, billing, rate-limit and general server failures do not trigger another paid generation. The cache is bounded and a changed endpoint can fall back again.

Native requests preserve generation controls and provider routing. Chat requests preserve routing, including data-collection restrictions and explicit false values. OpenRouter's native image provider schema does not currently advertise `require_parameters` or `data_collection`; forwarding them is not proof of native enforcement. Required native controls need endpoint verification, an explicit native protocol and output inspection. A data-collection routing requirement needs an eligible chat route, or a user-approved change to incompatible requirements. Controls that the SDK chat API cannot express are listed in the result and UI. `require_parameters` rejects such a downgrade locally before that request. The app's response timeout and cancellation signal apply to both protocols; a timed-out or cancelled call cannot subsequently save an image.

The native provider consults the source OpenRouter credential for every request, including held model references. Credential removal unregisters its mirrored catalog; rotation updates it even when key length is unchanged. A 401 is retried only when a newly resolved credential differs. Payload/response callbacks, request headers and a supplied fetch implementation remain supported.

OpenRouter's reported usage is retained on the top-level tool result, including failed saves and charged provider failures. The chat adapter captures actual response billing before the SDK estimates token prices. Session statistics and cross-session usage therefore count the image request once under its OpenRouter model. Details provide the UI's cost summary and do not create a second usage entry.

## Files and committed receipts

Before contacting the provider, references must be valid supported raster images and destinations must satisfy the session's file policy. Inputs are bounded per image and in aggregate. A dotted directory remains a directory; an explicit filename can be used only for a single requested image.

Provider responses and decoded image dimensions are bounded. The entire returned batch is decoded and validated before its first write. Raster originals stay byte-for-byte; the actual encoding determines the extension. SVG originals are retained with a raster preview and reject active content and external images.

`image-files.ts` stages complete bytes beside the destination, syncs them, rechecks live admission and canonical paths, and atomically publishes. Without overwrite, exclusive publication cannot truncate a file created during the provider wait. Explicit overwrite replaces a complete file atomically. Automatically assigned names use a short prompt-derived stem and numeric collision/batch suffixes; they contain no automatic model or timestamp metadata. Prefer an explicit content-related filename. No staging file is reported as an output.

A later failure can leave earlier committed images. The failed result retains only those actual writes, their previews and request usage. Rewind uncovered-path consent, persisted child-write evidence and Library consume the same validated receipts. Generated images are excluded from transcript and review changed-files lists, including child-run outputs; their write evidence remains available to Rewind. Failed intent and unsaved destinations remain absent. Generated Library items preserve the original path/name and archive full original bytes; inline-only historical images keep their existing stable identity.

## Renderer

`image` calls remain independent transcript rows, including adjacent image calls; they never fold into the Changes group. `ImageGenerationResult` composes the vendored beUI `ImageGeneration` media and actual queued/generating/complete/error states. Pending requests reserve one thumbnail per requested `n`; settled requests show only actual outputs. Images arrange horizontally and wrap according to available content width. Default results contain only media: prompts, filenames and other metadata do not reserve a caption or determine layout.

Hover or keyboard focus reveals floating Information actions, plus Retry/Cancel on delivered generated images. Non-hover devices retain visible actions. One shared beUI information popover per generation opens beside the selected image and includes its complete name/path, actual dimensions, size, MIME type, complete original/revised prompt, model, billing, warnings and errors. During a retry it shows only the prompt and current waiting state; the previous image's filename, dimensions, billing and other receipt information remain hidden. Settled information uses the displayed image's receipt or the failed attempt's diagnostics. Long information uses a bounded, keyboard-scrollable viewport and shared scroll fades; it never truncates prompt text or changes gallery geometry. File actions and enlarged images retain shared file navigation and `ImagePreviewProvider`. English, Simplified Chinese and Taiwan Traditional Chinese use app dictionaries. App and live OS reduced-motion preferences stop the decorative canvas.

The enlarged viewer uses Left/Right arrows and matching beUI controls to navigate only its source collection, with a position counter and bounded ends. Each image tool result is a collection; a settled delivery section shares one collection across its generation records. Delivered slots contribute the original followed by successful retry versions in creation order, then the next slot. Queued, generating, failed and cancelled attempts add no image. A retry completing while the viewer is open updates the collection without replacing the selected image. Switching resets zoom/pan and updates the caption, dimensions and local-file action while preserving the modal and keyboard focus. Composer/editor attachments, individual user/custom messages, tool image outputs, each Markdown surface and notebook cell outputs use their own independent collections.

## Generated-image delivery and private replay

The skill and tool guidance require `present` for every committed image, including edits and partial batch successes. `present` recognizes generated images from matching committed `image` receipts on the complete selected branch, not extensions or filename patterns. Ordinary images retain their file cards. Only the bottom delivery gallery receives generated-image media and controls; the `present` tool disclosure retains its original text result. The gallery uses the same `ImageGenerationResult` component as the image tool, including media ratios, waiting surface and on-demand information. Adjacent delivered generations share horizontal gallery space even when their prompts differ. File media streams through the existing custom scheme.

Generation records retain private SHA-256 identities for the committed original bytes. A renamed destination can keep its generated display and replay when its bytes match and the original path has been retired; matching size or filename alone is insufficient. Historical raster receipts can supply exact saved image bytes to recover the same association. Reopening or resource reloading an idle session backfills missing presentation metadata in private `pith_image_presentation_v1` entries. The display transcript projects those entries onto the original successful delivery; original SDK messages, provider context, image bytes and frozen request arguments stay unchanged. Repeated recovery is idempotent, and every delivered batch member uses its own verified current path.

`image-replay.ts` freezes original arguments/results in SDK custom entries (`pith_image_generation_v1`). Presentation details carry display metadata only; a request-copy guard removes that metadata before provider calls while preserving the persisted display. Supporting replay arguments never enter the tool schema, result prose or model requests. The SDK excludes custom entries from model context. Each retry is main-owned direct execution of the first-party image implementation; it never prompts an LLM or inserts assistant/tool messages. Its renderer IPC contains only session, generation, file and selected-history identity.

Replay requires the matching successful presentation on the current selected branch and an idle, writable normal parent session with the app-owned image tool active. It keeps the original prompt, references, controls and routing, setting `n` to one and freezing an omitted model to the model that produced the original. The file destination is a new numeric variant beside the selected source; the saved original and literal stored request arguments are retained. Reference files are read again from their saved paths, so missing references fail and externally changed reference bytes are not an immutable snapshot. A seed does not promise identical pixels.

Private `pith_image_replay_v1` entries persist queued/running/settled states, explicit cancellation, the selected prior attempt and committed file receipts. Snapshots fold state updates by attempt identity, preserving every retry in selected-branch order. Each image's history starts with the original and includes every successful, failed or cancelled attempt. Left/right buttons and a position indicator share the image’s top toolbar with Information and Retry/Cancel. The toolbar appears only on hover or keyboard focus (also visible on non-hover devices), without changing gallery geometry. Information and enlarged previews follow the selected version. A new retry selects its waiting version automatically; browsing older versions during generation does not cancel the operation. Manual cancellation restores the image selected before retry; retrying a failed attempt uses its prior saved image as the cancellation fallback. A failed retry displays an empty media surface with its failure message. The original and earlier attempts remain accessible through history. Reopening restores all records and marks an interrupted request without automatically issuing a paid replay. Per-image Retry/Cancel controls share the generation waiting surface. Typed revisioned metadata stays outside transcript event sequencing. Plan work registration and checkout tool leases fence mode changes, reload and Rewind; cancellation/admission is checked again before saving. Standalone SDK usage retains billing once; Library history extraction and Rewind coverage consume the private committed receipts.

## Verification

Run `npm run typecheck && npm run build`, then `npm test -- --no-prepare --suite image-skill --suite image-replay --suite image-tool --suite image-tool-ui --suite image-safety --suite system-prompt --suite extension-startup --suite plan-mode --suite sdk-tool-boundary --suite tool-catalog --suite usage-stats --suite rewind-sdk --suite subagents --suite written-file-preview --suite library --suite library-ui --suite transcript-rhythm --strict-skips`.

The image suite uses offline HTTP/provider fixtures, real SDK sessions and filesystem races. The UI suite renders production components in Electron; `PI_IMAGE_SCREENSHOT_DIR` retains screenshots. Live smoke checks use the configured account and incur provider charges: generate an image, edit that saved reference, verify its decoded bytes and top-level usage. Provider availability and every model's image quality are outside offline coverage.
