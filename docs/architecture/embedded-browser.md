# 内嵌浏览器（右栏 Browser 面板 + `browser_*` 工具）

> 2026-09-17 自 pi-web worktree `native-subagents`（webview 统一架构）移植；参考实现的权威文档是 pi-web `docs/architecture/embedded-browser.md`，本文件是 pi-app 命名/宿主下的改写。**以代码为准**——发现失配先改代码或同步本文；AGENTS.md 只保留不变量与指针。实测铁律见下方陷阱表；设计基线与决策记录见 `docs/superpowers/specs/2026-09-17-embedded-browser-design.md`（§11 为铁律的 canonical 版本）。

- **架构总览**：pi-app 恒为 Electron 桌面形态，无 pi-web 的 web 模式分支。主进程持唯一 `BrowserService` 单例（[src/main/browser/service.ts](../../src/main/browser/service.ts)，`initBrowserService`/`getBrowserService`，无 pi-web 的 `globalThis` 热重载守卫——main 无 HMR），经 playwright-core `chromium.connectOverCDP("http://127.0.0.1:<port>")` 连**壳自身**的调试端口，guest target 以 Page 形态浮现于 `contexts()[0]`。human 与 agent 页同为 renderer 托管的原生 `<webview src=markerUrl partition="persist:pith-browser">`（输入/IME/剪贴板/滚动全原生），**同一 guest 双驱动**：agent 工具与人看/操作同一个 webview，agent 工作时人可直接接管；人在 guest 上的原生输入经主进程 `input-event` 中继 `bumpInteraction`（进程内直调，无 pi-web 的 HTTP `POST /api/browser/interact`；按 contents 300ms 节流），递增 interaction generation 使旧 snapshot ref 失效（`StaleSnapshotError` 引导重新 snapshot）。登录态共享持久化 partition——这正是首次使用一次性 consent（`browserConsent`，写 `app-settings.json`）的告知点。

- **调试端口常开**（[cdp-port.ts](../../src/main/browser/cdp-port.ts)）：`appendCdpSwitches(pickCdpPort())` 在模块顶部、app ready 前——`appendSwitch` 之后无效，开关式启用会要求重启应用，且建页握手依赖确定性连接。端口随机 19000–38999、仅 127.0.0.1，`PITH_CDP_PORT`（1–65535 整数）可覆盖（检查脚本固定端口即用它；`check-browser-ui.mjs` 另有 `PITH_CHECK_CDP_PORT` 逃生口）；必须同时挂 `remote-allow-origins=http://127.0.0.1`，否则 playwright CDP WebSocket 的 Origin 头被拒。`getCdpPort()` 是 service 初始化取端口的唯一途径（与 Chromium 实际生效一致）。残余风险接受：本机任意进程理论上可连此端口驱动 app（本地攻击者本已等价于用户）。

- **建页握手（控制反转）**：Electron 的 CDP 不实现 `Target.createTarget`（陷阱 1）。`createPage` 入队 `pendingCreates`（`getStatus` 暴露给渲染端）并挂起等待（15s 超时 `BrowserHostUnavailableError`）；Workspace 订阅 `browser:state`，见 agent owner 的 pendingCreate 且 browser 面板未开即 `openSidePanelTab('browser')`（事件驱动，取代 pi-web 的 2.5s 轮询兜底；human 的 pendingCreate 不自动开面板）；`BrowserPageView` 把 pendingCreate 物化为 marker webview，`dom-ready` 后经 `browser:seen` 握手（上报 wcId；**建页首跳导航交服务端 `goto`**——renderer 自导航会输掉与 reconcile 的 marker 竞态）；reconcile（1s `unref` 轮询 `context.pages()`）按 marker 登记 runtime 后 waiter 放行。`registerExternalPage`（`browser:seen`）兼作 state-only 兜底：CDP 连接前已存在的 guest 不进 `context.pages()`（陷阱 7，Electron 43 起实测），先按上报登记，target 随后浮现时 reconcile 升级为完整登记。

- **关页由 renderer 驱动**：webview guest 的 `page.close()` 永久挂死（陷阱 2）。`closePage` 只摘注册表（`closingTargetIds` 给两个轮询周期的宽限，防 reconcile 按 marker 重登），renderer 下一轮 `browser:state` 发现页面消失即卸载 `<webview>`（guest 随之销毁），reconcile 的消失清扫兜底。最后一页关闭 → `onBrowserEmpty` → Workspace `closeSidePanelTab('browser')` 自关面板标签。

- **三态可见性铁律（陷阱 3）**：选中页正常渲染；**未选 agent 页 `opacity: 0` + `pointer-events: none` 全尺寸托管，绝不可 `display: none`**——display:none 的 guest click 超时、screenshot 永不返回、`fill` 静默无效（实测），opacity 形态下 timer/rAF 满速、click/pressSequentially/screenshot 全部可用；未选 human 页维持 `display: none`（无服务端驱动，省资源）。判据在 [BrowserPageView.tsx](../../src/renderer/src/components/app/BrowserPageView.tsx) 的 IRON RULE 块。webview 的显式像素定尺寸（ResizeObserver）也是三态的配套：`display:none → visible` 的过渡中 guest 实测尺寸滞后，布局必须由 host 驱动。

- **agent 页归属与回收**：owner = `HUMAN_OWNER`（`"human"`）或 `agentOwner(sessionId)`（`agent:<SDK session id>`，fork 不变）。弹窗按**系统浏览器语义**分流（[wiring.ts](../../src/main/browser/wiring.ts) 的 `popupOpensWindow`）：窗口形态的 `window.open`（disposition `new-window`，或 `default` 但 features 里带窗口特性——尺寸/位置/popup/menubar 等）直接 `allow` 出一个真 `BrowserWindow` 弹窗；标签形态的（`target=_blank`、⌘/Ctrl+点击、裸 `window.open`，disposition `foreground-tab`/`background-tab`/无 features 的 `default`）才 deny 后以 `browser:popup` 事件收口，由渲染层按 marker 流程物化成面板标签页（owner 经 opener 的 webContentsId 从 `wcIdMapRef` 继承，agent 页的弹出归 agent）。真弹窗窗口**不进面板注册表**：与面板页同分区（cookie 罐共享，登录后 opener 侧才算登录）、保留真实 opener 关系（SIWA/Google 的 `postMessage` 弹窗握手因此成立）、随 opener 的 guest 销毁而关闭（面板折叠/关页/会话结束都不留指向已死 opener 的窗口）、开弹窗的弹窗同样按 guest 语义分流。marker URL 一律 deny 只记日志；壳窗口 http(s) deny + `shell.openExternal`。会话 dispose（`disposeManaged`）与删除（`deleteSession`）→ `closePagesForOwner(agentOwner(id))`；运行中止**不**关页（跨 turn 保留，与 pi-web 一致）。

- **IPC / 事件面**（HTTP 路由 → 类型化 IPC，DTO 进 `shared/types.ts`，[ipc.ts](../../src/main/ipc.ts) 注册、[preload](../../src/preload/index.ts) 逐一暴露）：`browser:status`（纯读，**不**踢 reconcile——标题会变的页面会让 notify→broadcast→getStatus→reconcile 以 ~30ms 节奏自持循环；target 发现由 1s reconcile 与建页/consent 后的显式拉取覆盖）、`browser:consent`、`browser:createPage`、`browser:closePage`、`browser:seen`、`browser:elementAt`（服务端 `resolveElementAt` 路径；UI 批注优先 renderer 侧 `executeJavaScript`）、`browser:theme`（失败静默——纯外观）、`browser:clearData`。事件经 `win.webContents.send`，**一律无 `eventSequence`**（`context_usage` 规则——给它们序列号会破坏 renderer 的快照/事件对账）：`browser:state`（完整状态快照；注册表任何变更——reconcile、agent 动作、建/关页、consent、crash——后推送，`notifyState` ~30ms 合并；renderer store 整体替换、浅比较无变化不通知）、`browser:popup`（**只承载标签形态的弹窗**；真弹窗窗口不经事件面）、`browser:download`、`browser:guest-shortcut`。

- **面板（Ruling H keep-alive）**：[BrowserPane.tsx](../../src/renderer/src/components/app/BrowserPane.tsx) 挂在右栏 `SidebarPanel` 的 keep-alive 层——**切换 rail 标签只是隐藏层，关闭浏览器标签才卸载 webview、销毁 guest**（`SidebarPanel.tsx` 的 keep-alive 注释；页面/滚动/播放状态跨切换保留）。`BrowserStore` 由 Workspace 持有（比面板活得长：rail 折叠与关标签一样卸载面板、销毁 guests，但快照仍在，重开即画——挂载首帧就物化恢复行，等待仅为内容重载，agent 页按原 owner 重新登记）。guest 聚焦时浏览器 chrome 的按键经 `before-input-event` 拦下（preventDefault 挡 guest 原生行为）以 `browser:guest-shortcut` 广播渲染层，由 BrowserPane 分流：⌘±/0 → zoom 阶梯、⌘F → 查找条、⌘P → `webview.print()`（Ruling M；仅本面板 rail 标签激活时接管；此通道**无可编辑目标守卫**——按键来自 guest 即面板实际激活，页面内输入框聚焦时浏览器按键仍优先，与 Chromium 一致）。面板自身快捷键（window 捕获 + stopPropagation）同理只在激活标签生效，但让位可编辑目标。

- **聊天外链 → 内置浏览器**（[markdown.tsx](../../src/renderer/src/lib/markdown.tsx) 锚点渲染器 + [open-link.ts](../../src/renderer/src/lib/browser/open-link.ts)）：偏好 `pi-app:open-links-in-browser`（默认开，Settings → Browser 可关）开时，明文左键 http(s) 链接 → `requestBrowserOpenLink(href)` 入队 + 派发 `BROWSER_OPEN_LINK_EVENT`（`pith:browser-open-link`）→ Workspace 开/激活面板 → BrowserPane drain 队列，按 popup 同款 marker 流程建 human 页并导航。修饰键点击、非白名单 scheme 走原生行为不变。

- **批注模式**（[BrowserAnnotate.tsx](../../src/renderer/src/components/app/BrowserAnnotate.tsx)）：capture 层拦掉 guest 全部指针事件且**批注模式全程常驻**（选中目标后也不撤，否则 guest 重新收到 hover/点击，页面元素被真实互动）；选中期间点击框内 = 取消、框外 = 改选。元素解析走 **renderer 侧 `webview.executeJavaScript`** 的 elementFromPoint 片段（与服务端 `resolveElementAt` 同源；trailing 节流 ~80ms + 序号守卫防乱序；点击与最近悬浮 <3px 直接复用）——服务端 runtime 在 renderer 侧导航后会滞留旧文档，webview 执行通道始终绑活文档。**滚轮必须显式转发**：`webview.sendInputEvent({type:"mouseWheel", x, y, deltaX, deltaY})`，只发纯像素 delta 且**符号与 DOM WheelEvent 相反（取反）**，**转发前按主轴清零副轴**（|dy|≥|dx| 判纵向；macOS 触控板几乎总带副轴噪声，不清零两轴都消费甚至整事件被吞）——带 `wheelTicks*`/`hasPreciseScrollingDeltas` 的 payload 在 guest 上被静默吞掉。滚动期间抑制悬浮高亮，停稳（最后事件后 250ms，macOS 惯性顺延）后在落点解析一次。Esc 退出（仅激活标签；文本输入让位）。提交 → `pith:browser-annotation` CustomEvent → Workspace → Composer 草稿插入。

`browser_snapshot diff` 的基线；旧实现拿未裁剪全文当基线，于是「开在模型从未见过的下半页」的模态框被 diff 报成 `(no snapshot change)`（实测 GitHub 设置页删除确认框），现在基线换成可见前缀，被截断时 diff 再追加窗口外提示。`maxChars` 与 `offset` 是**每个会回快照的工具**的参数（不止 `browser_snapshot`）——长页面上动作结果常常正是被截断的那一份，而动作之后想读窗口外就不该再补一次整页快照。窗口起点会吸附到行首（字符 offset 会切在行中间，实测 3000-7500 那窗的第一行是半截 `[ref=f1e92] [cursor=pointer]:`），但吸附必须保证窗口仍能推进：整页一行时行首永远是 0，无条件吸附会让 next 停在原地、模型原地打转。`selector` 走 Playwright 选择器语义：strict 单匹配优先，多匹配退到唯一可见元素（真实站点整组 dialog 常驻 DOM，`dialog` 实测命中 5 个），仍不唯一则报出两个计数与 `:visible` / `>> nth=0` 出路。**「快照里看不出来」的动作都有 app 自产回报**：空 a11y 树附页内 measure 的诊断（readyState / `<body>` 子元素数 / 文本长度——把「确实没有可访问内容」与「建页脚本挂了」分开，实测那个 `body` 里只有 `fetch()` 的页）；滚动回位置与总量（`y/maxY`、viewport、下方还剩多少、文档尺寸），按键在焦点与上次不同时报元素标签名（只报变化，不刷噪声）；`browser_close` 接受 `pageId`（省略即关活动页），只回 app 自产的 page id——绝不把页面自报的 url/title 放到不可信边界外。**页面自报的错误必须包在它自己的不可信边界内**：`pageerror` / `console.error`（有界 8 条、同文本去重、只报上次快照之后的增量）是页面自写文本，放进边界外等于让页面往边界外注入指令，所以框外只有 app 自产的引导句。**长快照可分页**：`browser_snapshot` 的 `offset` 把窗口往后移，截断说明直接给出「下一段用 offset=N」——快照是文档序前缀（滚动不改变它），所以这是读长页面唯一可靠的方式（模型不必猜 CSS）；`offset` 越界时显式说「超出结尾」，不给一个空块。**动作后「无可观察变化」是强信号**：`settleForSnapshot` 的采样结果不再丢弃，但只在 mutation=0 **且**交付给模型的 a11y 文本与上次一字未变时才出声——真实使用证明只判 mutation 会大面积误报（勾选框真的勾上了、导航把整篇文档换掉，都收到过「无变化」）；「没测过」（零预算）与「测了是 0」严格分开，纯 `browser_snapshot` 不是动作、滚动的 `expectChange:false`，两者都不出声。**`browser_type` 有 8000 字符上限**：铁律 4 禁 `fill()`，长文本只能一键一键重放，超限时工具层直接返回明确错误（既履达页面，也不让它变成 8s 超时）。**上传（`browser_upload`）是真实能力，不是「点按钮看运气」**：`setInputFiles` 直连（ref 就是 `<input type=file>`——真实站点最常见的形态是把它 `display:none` 藏起来只暴露一个样式化按钮，直连不要求元素可见，label 由 playwright 自己 retarget 到控件）失败后回退到「订阅 `filechooser` + 真点 ref + `chooser.setFiles()`」，两者共用同一个 `ref`。**订阅 `filechooser` 本身就是机制**：playwright 只在客户端订阅该事件时才发 `Page.setInterceptFileChooserDialog{enabled:true}`（`_updateFileChooserInterception(initial)`：`if (initial && !enabled) return`），所以订阅期间 Chromium 的原生文件面板被拦下、事件交给我们——旧行为是原生面板挂在 guest 上、这轮点击拖到 8s 超时（且无人能填）。**`browser_click` 因此带防护**：点击前先订阅（`CLICK_PICKER_GUARD_MS` = 1.5s），事件到达即抛 `FilePickerInsteadOfClickError`；早于点击完成到达的在 race 里判负，晚于点击完成的在 settle 之后、返回结果前再判一次（两个异步消息的真实可能顺序；漏报会让模型以为点成功了，而页面什么都没发生）。防护窗结束后拦截随之关闭。**代价要写清楚**：拦截是**页面级**的（playwright 只能整页开关），所以这 1.5s 内**人**在同一个 guest 上点上传控件也会被拦下——那次点击不弹面板、也不会选出任何文件，窗口过后人再点一次即可。窗口很短且只在 agent 点击期间存在，但“人的上传不受影响”是错的（复核指出），不能这么写。**路径预检在工具层**（[tools.ts](../../src/main/browser/tools.ts) `resolveUploadPaths`）：绝对路径、或按会话 cwd 解析的相对路径；必须存在、是常规文件（目录/设备节点拒绝），单次 ≤ 20 个。**任意目录：owner 明确要求「暂时允许任意目录上传」**，所以刻意不做 cwd/沙箱收窄——页面只拿到文件内容（Chromium 自己从磁盘读，拿不到路径清单），但被注入的模型理论上能把任意可读文件送到页面；这条以 `TODO(sandbox)` 标在 `resolveUploadPaths` 上，与 edit/write 的 DSH 沙箱对齐时应收窄可读根。上传结果附 app 自产的 `[Attached N files: …]` 说明（页面常只用图标表示已选文件），表单仍需模型自己点提交。**每个动作目标有三种形态：`ref` / `selector` / `ax`**（`click`/`hover` 三种都收，`type`/`select`/`upload` 只收前两种；恰好给一个，工具层 `validateTargetParams` 预检）。`ref` 来自最近一次快照（带 generation / allow-list 校验）；`selector` 是 Playwright 选择器，**逐 frame 查找**（`page.frames()`，最多 20 个）——这条路覆盖 iframe 内的控件（本地 fixture 实测：主 frame 无该按钮、它在子 frame 里，`button#deep` 解析为 `in frame #1` 并真点中）。**注意：小红书那个底部栏最后查明不属于这一类**（见下 `ax`），早先「它在子 frame 里」的判断来自一个漏走 `node.shadowRoots` 的探测脚本，已撑回。候选规则：先收「唯一可见」的那一份（同一控件常在多个 frame 各留一份，隐藏的不算），再收「唯一匹配」（不可见也接受——hidden `<input type=file>` 正是上传要的形态）；多个 frame 同时命中或单 frame 内多匹配都报定向错并逐 frame 列出（选择器**无法**指定 frame，只能让模型写得更具体：`:visible` / `>> nth=0`）。命中后附 app 自产说明 `[Targeted by selector … in frame #N (url).]`，否则多 frame 页面上模型无从知道刚才点的是哪一份。**闭阴影根（closed shadow root）任何选择器都进不去，而且它通常也不在 aria 快照里**——Playwright 的 aria snapshot 只看得到 open 根（实测：同页 open 根的按钮列在快照里、closed 根的那一个不列，于是「优先用 snapshot + ref」在这类控件上是死路，错误文案已改成指向 `ax`）。实测形态：小红书创作平台的底部栏是自定义元素 `<XHS-PUBLISH-BTN>`，「暂存离开」与「发布」两个按钮在它的 **closed shadow root** 里；宿主在 light DOM 但正文为空，字符串只以 `save-text` 属性存在（这正是「只看得到属性/脚本串」的原因）。`ax` 形态就是为它存在的，链路每一步都实测过：`Accessibility.getFullAXTree` → `backendDOMNodeId`（闭合根里的按钮也在）→ `DOM.getBoxModel`（120×40 @ 57,758）→ `DOM.getNodeForLocation` **命中校验** → `Input.dispatchMouseEvent`（真实指针事件，不是 `.click()`）——全部挂在 playwright 的 `context.newCDPSession(page)` 上，不需要 `webContents.debugger`。名字先严格匹配、再退到大小写不敏感；不给 `role` 时优先取可点角色（同一标签在 AX 树里还有 StaticText/InlineTextBox 副本，否则「一个按钮」会变成「多个同名元素」）；同名候选先用布局盒筛出「渲染中的那一份」，仍不唯一就报歧义并让模型加 `role`。**命中校验是安全属性**：盒内九个候选点（中心 + 四分之一 + 边中点）逐个问 CDP「这个点上最顶层是谁」，只有命中目标本身或它的祖先（点到按钮内部文字节点）才算数；全不通过就报「被 X 盖住」并**一个指针事件都不发**——实测那两个点的最上层元素是 XHS 自己的菜单容器（`d-new-menu`），而旁边 144px 就是不可撤销的「发布」。`ax` 点击同样装配 `filechooser` 护栏（闭合根里的上传按钮不得弹出原生面板）。局限：闭合根里的**输入框**仍靠 ref/selector——`ax` 只承担 click/hover 两种真实指针动作。注意 `browser_snapshot` 的 `selector` 仍只作用于主 frame（它是对主 frame 做子树快照）：跨 frame 的是**动作目标**。执行语义（全部 service 层，实测纪律）：文本输入走键盘事件链 `click → ControlOrMeta+A → pressSequentially`（**禁 `fill()`**——陷阱 4）；`agentScroll` 先 CDP mouseWheel（视口中心）再校验 scrollY，被吞时 `window.scrollBy` 兜底（陷阱 5）；snapshot = `ariaSnapshot({ mode: 'ai' })`、ref allow-list 全量重建、`selector` 子树 / `diff` 行级差异；**动作后快照先 settle**：120ms 预热 → URL 变化或 evaluate 失败判导航中 → 等 domcontentloaded；否则 MutationObserver 120ms 采样连续两次静默才快照，持续繁忙页面按 1.5s 预算截断（计时经 `BrowserServiceDeps.settle` 可注入，单测归零）；**页内求值全部走同一个预算入口**（`evaluateWithBudget`：service 里唯一直接调 `page.evaluate` 的地方，`scripts/check-browser.mjs` 有来源钉）：`page.evaluate` 没有超时参数，裸用它一次卡住的页面就能把 `withPageLock` 与 `agentBusy` 永远占住（settle 采样、滚动位置校验、annotate 的 canvas 合成、reload 兜底、人工批注的 elementFromPoint 都改成带预算）；**两档预算**：动作与导航沿用 8s/20s，纯量测（滚动位置/视口/焦点/空树诊断/reload 兜底/人工批注坐标，即「量不到就不出声」的那类）用 `MEASURE_TIMEOUT_MS = 1s`——否则一串量测就能把一次点击帧成几十秒；求值返回三态（ok / timeout / error），**超时与「页面里抛错」必须分开**——settle 靠后者判「导航中」，合成一个 null 会让导航检测失效；单次采样用 settle 的**剩余预算**，所以卡死的页面只能拖到预算用尽而不是更久，且量不到时不再编造「无变化」；同样地，滚动量不到前/后位置时宁可不动作（不发 wheel、不 scrollBy），也不冒双滚的风险；`browser_wait_for` 两个独立旋钮、都是秒：`delay` 是先固定睡（夹到 [0,30]s，发生在任何条件之前），`timeout` 是**每个**条件的上限（0.5–30s，缺省 5s）；条件超时不吞，未满足条件列在不可信边界外；screenshot = JPEG q60、显式 5s 超时 + 8s 重试一次（陷阱 8），annotate 标签在页内离屏 canvas 合成（≤50 个，不进 DOM、失败静默回退原图；框选与合成共用同一个 8s 预算）；全部交互/导航 8s/20s 超时，绝不容 playwright 默认 30s 挂死。每次工具结果的 `details.pageId` 是动作落点（列表工具带活动页、关页带被关的那页；不知道时不写），`kind: 'pi-app-browser'` 用于归因。错误映射各有明确文本（`ConsentRequiredError` 引导用户去面板确认——模型不得代确认；`BrowserHostUnavailableError` 引导开面板；Stale/InvalidRef/PageGone/PageNotFound/NavigationBlocked 同）。**建页握手自带重试**：`createPage` 在 pendingCreate 在途时按 1s 重推 `browser:state`（renderer 漏掉首次推送即自愈），超时后换新 pendingCreate 重试一次，两次都失败才上报——冷启动的第一次握手会输掉竞态（renderer 尚未挂载宿主 / marker target 尚未对 CDP 可见），旧实现把这次重试推给模型，导致每个会话的第一个 `browser_navigate` 都要先失败一次（实测）。元素解析用页内 `elementFromPoint`（陷阱 9）。

- **工具注册门控（四处同步清单）**：14 个名字必须同时出现在——① 激活集（[manager.ts](../../src/main/pi/manager.ts) `initializeSession`/`applyActiveTools`，`browserToolsFlag ? APP_BROWSER_TOOL_NAMES : []`）；② `catalog.ts` 的 `APP_TOOL_NAMES`（builtin 分类）；③ [tool-icons.tsx](../../src/renderer/src/lib/tool-icons.tsx)（每工具一枚映射）；④ [tool-categories.ts](../../src/renderer/src/lib/tool-categories.ts) 的 `browser` 类别。**注册本身 service 门控，永不做 flag 门控**：`buildSession` 的 `customTools` 在 `getBrowserService()` 存在时注册（子会话路径同样注册——子代理 profile 可按名授权，frozen ceiling 按名放行），因为 customTools 数组在 build 时冻结、SDK 每次注册表重建复用它，而 `setActiveToolsByName` 静默丢弃未知名字——flag 门控注册会让 Settings 的开关对既有会话永远无效。**开关即时生效**走 `setAppendPrompt` 模式：`setBrowserAgentTools` → 空闲会话立即 `reload()`，流式会话等 `agent_settled` 补；SDK reload 会重新激活全部已注册工具，所以 `reloadManagedSession` 在 reload 完成后**重应用激活集**——这一步才是关掉开关时移除 browser_* 名字的机制。首次使用还需 consent，`ConsentRequiredError` 由 `browserToolErrorText` 转成引导文本。

**webview / 批注附加陷阱**（同表地位，无编号）：

- `allowpopups` 必须以**字符串属性**展开写在 `<webview>` 上（React 剥布尔属性，裸 `allowpopups` 无效）；它同时也是真弹窗窗口的开关——没有它 Chromium 在 `setWindowOpenHandler` 之前就吞掉 `window.open`。
- 真弹窗窗口的 `partition` 必须显式写进 `overrideBrowserWindowOptions.webPreferences`（Electron 只承诺继承“安全类” webPreferences；实测即使不显式给，cookie 罐也会随 opener 继承下来，但不要靠这个默认值）。**尺寸**取 features（缺省 800×600，夹在 320×240 与工作区之间），**位置一律居中**到壳窗口所在显示器的工作区（`popupWindowGeometry`）：忽略 features 的 left/top 是刻意的——Apple 的 SIWA 弹窗写 `left=0,top=0`，不接管就停在屏幕左上角，而不写位置的站点又落任别处，同一个 app 两种落点；实测 handler 给的 x/y 能压过 features 解析出的 left/top。
- **创建真弹窗窗口会让 opener guest 掉一帧内容**（用户报的“原页面闪一下”；**owner 已决定接受，不改行为**）。完整根因实测（2026-09，最小复现台 = Electron 壳 + `<webview allowpopups>` + 暗底 fixture（`#101010`）+ guest 自身目标的 CDP screencast 逐帧平均亮度 + 页内 rAF 计时）：① 带 opener 关系的弹窗，初始 about:blank **必然继承 guest 的渲染进程**（同 OS pid；跨源目标、弹窗侧 `sandbox: true`、guest 侧 `sandbox`、guest 侧 `nativeWindowOpen` 均不改变——后者 Electron 44 已无效）；② BrowserService 的 playwright 连接对新 target 的 **auto-attach（`waitForDebuggerOnStart` 暂停 + Runtime/Page/Network 初始化批次）恰好命中弹窗诞生窗口**，共进程 guest 主线程冻结 16-33ms 并提交一帧受损内容（screencast 实测 27.8 → 16.9 → 27.8 / 21.5，rAF 单间隙 33-35ms；shell DOM/尺寸/可见性、窗口 focus/blur、guest 的 `dom-ready`/重载/`document.hasFocus()` 全程无变化）。复现台里没有第二条 CDP 客户端时弹窗创建**完全无闪**；弹窗就绪后同一初始化批次**完全无害**（pw 晚连接实测）。**已证伪的修复，勿重试**：弹窗/guest 全部 webPreferences 杠杆与显示时机（不传 overrideOptions / defer / `show:false`+`ready-to-show` / `setDevToolsEnabled(false)`）；`noopener`（分进程后无闪，但 opener 语义必失）；deny + 自建弹窗（`window.opener` 是 LegacyUnforgeable，任何注入都伪装不了，SIWA/Google 握手必断，连 contextBridge 都遮蔽不动）；延迟 attach 事件投递（暂停在 Chromium 侧从 target 诞生即生效，延迟只拉长冻结——TCP 暂停实测 612ms）；`Target.setAutoAttach` 的 filter（exclude-page 与 include-webview 两变体都让被过滤掉的弹窗**永久冻结**：filter 只裁事件投递、不阻止暂停，被裁掉的弹窗无人能释放）；patch playwright 做 popup fast-path（`waitForDebuggerOnStart:true` 下释放速度无关，单命令释放仍是 33ms 地板）；`waitForDebuggerOnStart:false` + 初始化批次照发（批次落在诞生窗口本身即卡，与暂停无关）；`waitForDebuggerOnStart:false` + 立即 detach（detach 在诞生窗口内同样致永久冻结）；`waitForDebuggerOnStart:false` + 静默保留会话（一次干净、复跑出现含无弹窗场景的随机死锁，不可信）。结论：保 opener 语义的修复空间已穷尽，接受这一帧闪；**不要再从弹窗选项、分区、显示时机或 pw 的 attach 行为上找原因**。
- 批注滚轮转发：纯像素 delta + 符号取反 + 主轴判定清零副轴；`wheelTicks*`/`hasPreciseScrollingDeltas` 载荷被 guest 静默吞掉（垂直/水平/小数像素均 1:1 生效的只有纯像素形态）。
- 缩放**每次 `dom-ready` 重应用**，不能与只执行一次的 marker 登记/首跳握手共用闩锁（跨 origin 导航会重置 guest zoom；批注框与页面分属两个坐标系就是它的症状）。
- 铁律 9 的 `DOM.getNodeForLocation` 在 `ax` 形态里仍然要用：`elementFromPoint` 进不去闭合阴影根，所以那里的命中测试只能用 CDP（实测：fixture 的闭合根里返回的就是那个 BUTTON，`includeUserAgentShadowDOM: true` 下还能回映射到 `backendDOMNodeId`，坐标**必须取整**否则 CDP 直接 `Invalid parameters`）。它只是**校验**而非定位来源（坐标来自刚取的 `DOM.getBoxModel`），校验不通过就不点，所以铁律 9 的「跨进程导航后不可靠」在这里表现为**报错**而不是点错；对应源断言也已从「一律不得出现」收窄为「恰好一次、且必须在 `cdpNodeAt` 里」。
- **agent 的按键不得驱动应用自己的 chrome**：CDP 派给 guest 的按键先交给窗口当前聚焦的 widget——壳窗口持焦点时它会 **同时出现在壳窗口 DOM**（实测：壳窗口的 keydown 探针收到了派给 guest 的 `F24`/`Shift`，agent 按 `Escape` 就会停掉本轮——`Escape` 是 Composer 的停止键），而 `<webview>` 拿到 DOM 焦点后同样的按键壳窗口 **一个也收不到**；鼠标事件不漏。**两个看似显然的杆杆实测都没用**（壳窗口 `activeElement` 始终停在按钮上、按键照漏）：main 侧 `webContents.fromId(id).focus()` 与 playwright 的 `Page.bringToFront`。真正有效的只有**渲染层把 `<webview>` 元素 focus**，所以 `BrowserService.focusGuestForKeys` 在**每次键盘动作前**发起握手并**等 ack**：`browser:focus-guest` → preload `onBrowserFocusGuest` → 面板按 `webContentsId` 找到元素并 focus → `browser:focus-guest-done`（1s ack 超时，面板关着也不会卡住按键），而且**每次重新断言**（用户点回提问框、页面导航都会把它拿走）；活验证在 `check-browser-ui.mjs`（壳窗口持焦点时按键漏进壳 DOM、`<webview>` 聚焦后零命中），顺序断言在 `check-browser.mjs`（`focusGuest` 必须被 await 且早于按键）。
- 设备模拟绝不走 CDP `setDeviceMetrics`：guest 视口必须等于 webview 元素，批注坐标系（元素 rect 原点 + `guestOffset()`）才有单一路径。
